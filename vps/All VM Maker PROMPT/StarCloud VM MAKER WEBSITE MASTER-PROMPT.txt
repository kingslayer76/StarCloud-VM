# GLOSSARY (so nothing gets misread — implement exactly these meanings)

**Virtualization:** **KVM** = hardware-assisted virtualization, full speed (needs `/dev/kvm`). **TCG** = QEMU's software emulation, 3–10× slower, used when KVM is missing. **QEMU** = the program that actually runs the VM. **cloud-init** = the tool that configures a fresh Linux VM on first boot (hostname, user, SSH key, packages). **cloud image** = a ready-made OS disk image (no installer needed). **ISO** = a full OS installer disc image (needed for Windows). **qcow2** = QEMU's disk file format (supports snapshots, thin allocation). **OVMF/UEFI** = modern firmware (needed for Windows 11 / Secure Boot). **virtio** = fast paravirtual drivers (disk/network) — Windows needs them injected. **unattended install / autounattend.xml** = Windows installing itself with no clicking. **cloudbase-init** = Windows' equivalent of cloud-init.

**Resources:** **vCPU** = virtual CPU core given to a VM. **over-allocation** = selling more vCPU/RAM than physically exists (fine for CPU, risky for RAM). **CPU pinning (vcpupin)** = binding a VM to specific physical cores (what makes a VDS "dedicated"). **hugepages** = pre-allocated large memory pages for guaranteed RAM performance. **NUMA** = memory is attached to specific CPU sockets; crossing sockets is slower. **ballooning** = taking unused RAM back from a VM. **thin provisioning** = disk file grows as it's used.

**Networking:** **bridge** = VM joins your real LAN and gets its own real IP. **NAT** = VM hides behind the host with port forwarding. **port forwarding** = host port 22001 → VM port 22. **rDNS / PTR** = reverse DNS (IP → name); mail servers require it. **allocation pool** = a reserved range of IPs/ports the panel hands out. **MTU** = network packet size. **VLAN** = a tagged virtual network segment.

**Console/Access:** **VNC** = remote framebuffer protocol → **noVNC** = VNC inside the browser. **RDP** = Windows Remote Desktop Protocol. **xterm.js** = the terminal emulator widget used in browsers. **SSH** = encrypted shell access. **guest agent (qemu-guest-agent)** = a small service inside the VM that reports OS/disk/network back to the host.

**Containers:** **LXC** = Linux containers (share the host kernel). **LXD/Incus** = a daemon + CLI on top of LXC that makes containers behave like light VMs (`lxc launch`, `lxc exec`); Incus is the community fork of LXD. **nesting (`security.nesting=true`)** = allowing containers to run *inside* a container. **Docker** = app-focused containers with images. **egg** = a Pterodactyl-style app template (image + startup command + env vars).

**Snapshots vs Backups:** a **snapshot** = instant point-in-time state on the same disk (fast, cheap, dies with the disk). A **backup** = a separate copy (can be offsite/encrypted, survives disk loss).

**Business:** **MRR/ARR** = monthly/annual recurring revenue. **proration** = charging only the difference when a plan changes mid-cycle. **dunning** = retrying failed payments automatically. **churn** = customers who left. **reseller / white-label** = someone sells your panel under their own brand. **GST invoice** = Indian tax-compliant invoice with GSTIN + tax split. **ToS/AUP** = terms of service / acceptable use policy. **SLA** = promised uptime.

**Security:** **Argon2id** = password hashing algorithm. **2FA/TOTP** = time-based one-time codes (Google Authenticator). **OAuth** = "login with Discord/Google/GitHub". **CSRF** = cross-site request forgery (token-protected). **rate limiting** = max requests per IP/route. **Turnstile** = Cloudflare's captcha. **disposable email block** = rejecting 10-minute-mail signups. **Let's Encrypt** = free auto-renewing TLS certificates. **Argon2 + HttpOnly + SameSite cookies** = baseline session hardening.

**Platform:** **EJS** = server-rendered HTML templates. **better-sqlite3** = fast embedded SQL database (one file, no server). **Socket.IO** = real-time push over websockets. **migration** = a versioned, idempotent DB schema change that runs on boot. **PWA** = installable web app with push notifications. **i18n** = multi-language UI (en + hi here).

# FEATURE SCOPE

## 0. Hypervisor auto-detection & capability engine (build this FIRST — everything depends on it)

On install and on every boot, the panel probes the host and writes a `host_capabilities` record + shows a **Capability Report** page in admin:

- **KVM**: `/dev/kvm` present + readable/writable? CPU virtualization flags (`vmx`/`svm` via `/proc/cpuinfo`)? Nested virtualization enabled (`/sys/module/kvm_intel/parameters/nested`)? User in `kvm` group?
- **CPU**: model, physical cores, threads, sockets, NUMA nodes, flags (aes, ssse3, avx2), current MHz, `lscpu` output.
- **RAM**: total, available, hugepages (`/proc/meminfo`), ballooning support.
- **Disk**: pools/mounts, free space per pool, backing filesystem, SSD/NVMe detection (`/sys/block/*/queue/rotational`), qcow2 vs raw support, thin-provisioning support, IO scheduler.
- **Network**: interfaces, existing bridges, MTU, public IPv4 (auto-detect via outbound probe **and** allow manual override), IPv6 availability + prefix, default gateway, DNS, VLAN support, `nftables`/`iptables` presence.
- **OS/tooling**: host distro + version (auto-pick the right package manager: apt/dnf/pacman), qemu/qemu-img versions, cloud-image-utils, xorriso, OVMF/UEFI, virtio drivers, python3, git.
- **Self-awareness**: is the panel itself running inside a VM? (then warn about nested virt), is it inside Docker?, available cgroup version (v1/v2), systemd present?

**Modes derived from the probe (user can also force them in Settings):**
| Mode | When | Behaviour |
|---|---|---|
| `kvm` | `/dev/kvm` OK | Full-speed VMs, hot-plug, live migration possible |
| `tcg` | no KVM | **QEMU software emulation** — must still work; show a persistent amber banner "Software emulation — expect 3–10× slower CPU", recommend max 1–2 vCPU / 2GB per VM, block huge VMs with a clear reason, and suggest containers instead |
| `lxc` | no KVM + LXC available | Container-based "VPS" product (fast, low overhead) |
| `docker` | Docker available | Container product line |

Rules: mode is **auto-detected, never required to be configured**; the create-wizard adapts (hides UEFI/SMBIOS/hot-plug options that TCG can't do, disables migration in TCG, caps resources sensibly); every VM card shows a small badge `KVM` / `TCG` / `LXC` / `Docker`; the hypervisor layer is a **driver interface** (`drivers/{kvm,tcg,lxc,docker}`) so modes are swappable without touching services/routes.

**Smart capacity guard (runs live):** "This host has 8 vCPU / 32 GB RAM / 400 GB free. You have allocated 6 vCPU / 24 GB. **2 more 4 GB VMs fit.**" Over-allocation ratio configurable; hard-block or warn-and-allow; auto-suggest the biggest VM that still fits; refuse to create a VM that would starve the host, with a human-readable reason.

## 1. Product lines (VPS · VDS · RDP · Bot Hosting) — sellable product types

> **HARD RULE (owner's explicit requirement):** a sold **VPS or VDS is always a real KVM/QEMU virtual machine — never an LXC/LXD container.** It must behave like a **Proxmox VE VM**: the customer gets a real kernel, can install *anything*, load kernel modules, run Docker/LXD/KVM inside, use VPN/WireGuard, edit sysctl, mount filesystems — **nothing is "unsupported"**. Nested virtualization must be exposed (`-cpu host,+vmx` / `kvm=on`) when the host allows it, and the capability report must say clearly whether nested virt is available.
> Containers (LXC/LXD/Docker) exist **only** as the separate cheap **Bot Hosting** product, never sold as "VPS".

Each product type is a plan category with its own create-wizard defaults, limits and UI:

- **VPS (shared KVM/TCG)** — over-allocatable CPU, shared cores, standard plans.
- **VDS (dedicated)** — **CPU pinning** (vcpupin to physical cores), guaranteed RAM (no ballooning, hugepages optional), dedicated disk IO limits, `cpu_mode=host-passthrough`, no CPU over-allocation, NUMA-aware placement, "dedicated cores: 4" shown clearly on the product card.
- **RDP / Cloud Desktop** — two flavours, same UX:
  - **Windows RDP**: Windows Server 2019/2022/2025 Datacenter templates from admin-uploaded ISO (bring-your-own-license, panel stores the note), automatic **virtio driver injection**, unattended install (`autounattend.xml`) or cloud-init cloudbase-init, auto-enable RDP + NLA, auto-generated strong password, per-VM RDP port, **web RDP client** (Apache Guacamole / Myrtille-style) so users connect from the browser with no client install, downloadable `.rdp` file, "RDP ready" detection by TCP port probe + cloudbase-init completion, Windows-specific metrics + reboot-safe console.
- **Containers (LXC/Docker)** — same UX as VPS, cheaper plans, instant provisioning, kernel-shared warning shown honestly.

### 1.1 LXD / Incus support & Bot Hosting (explicit requirement — must be first-class, not an afterthought)

Customers must be able to run **LXD containers inside their VPS/VDS** (e.g. to host Discord bots), and the panel must also be able to **sell LXD containers directly** as a cheap product.

**A. "LXD-ready" VPS & VDS (every Linux VPS/VDS):**
- LXD (or **Incus**, the community fork — support both, auto-prefer whichever the guest has) is **pre-installed and pre-initialized** by cloud-init, so the customer's very first command works:
  `lxd init --preseed` equivalent must already be done → storage pool created (`zfs`/`btrfs` if the disk supports it, else `dir`), `lxdbr0` bridge up, user added to the `lxd` group, no sudo prompt, no interactive wizard.
- VPS/VDS are **KVM VMs**, so LXD runs natively inside them with zero tricks (real kernel). Only the separate **Bot Hosting** product uses LXC containers, and there `security.nesting=true` (unprivileged) is set so customers can nest containers.
- The VM card shows an **"LXD ready"** badge, the installed version, storage pool + free space, and a **copy-paste quickstart** box:
  `lxc launch ubuntu:22.04 mybot` → `lxc exec mybot bash` → run bot.
- Optional guest-agent endpoint so the panel can **list / start / stop the LXD instances running inside a user's VPS** and show "3 containers running" on the VM card (read-only by default, control only if the user enables it).
- Nested-container resource usage counts against the parent VM's quota and is shown honestly.
- If the host is in **TCG mode** (no KVM), LXD-inside-VM still works (containers don't need nested virtualization) — the panel must say so instead of blocking it.

**B. "Bot Hosting" product line (panel manages LXD on the host directly):**
- Panel creates LXD/Incus instances itself → cheapest plans, ~2 second provisioning.
- **Bot/app templates ("eggs")**: Discord.js, Discord.py, Java (JDA), Node.js generic, Python generic, n8n, Minecraft (Paper/Fabric), and **import of Pterodactyl-compatible eggs**. Each template defines: image, startup command, env variables (shown as a clean editable UI), ports, min RAM.
- Per-instance: file manager, live console (xterm), auto-restart on crash + crash-loop detection, restart schedule, env-var editor, one-click **deploy from a GitHub repo** (branch + build command), resource limits via LXD profiles, port allocation, backup/snapshot.
- Discord/Telegram webhook on bot crash ("your bot went down at 3:12 AM, restarted automatically").
- Storage: detect ZFS/Btrfs on the host at install; if absent, use `dir` pool and say so. Snap-based LXD on Ubuntu 22.04+ must be handled (or use Incus from the official repo) — the installer must not fail on either.

**C. Terminology rule:** in UI and docs always distinguish clearly: **KVM VM** (full virtual machine) · **VDS** (VM with dedicated cores) · **LXC container** · **LXD/Incus instance** · **Docker container**. Never mix the words up.

## 3. VM lifecycle (QEMU/KVM)
Create wizard (5 steps, live "deployment blueprint" summary + live deploy log):

|---|---|---|

## TOPIC 3 — Product Lines (jo tum bechoge) + LXD

### VPS vs VDS vs RDP vs Container — farak kya hai?

| Product | Aasaan matlab | Kisko bechoge |
|---|---|---|
| **VPS** | Ek room jisme AC **saare floor ke saath share** hota hai. Sasta. | Normal users, students, bots |
| **VDS** | Ek room jisme **AC sirf tumhara hai** (dedicated CPU cores, guaranteed RAM). Mehnga, fast, stable. | Business, game servers, database |
| **RDP (Windows)** | Windows computer jisko tum browser se ya Remote Desktop se chalate ho. | Windows users, trading, software |
| **Container (LXC/Docker)** | Room nahi, sirf ek **almari ka dabba** — kernel share hota hai, isliye bahut sasta aur 2 second me ready. | Bot hosting, chhoti sites |

**VDS kaise "dedicated" hota hai (2 technical cheezein):**
- **CPU pinning** = VM ko CPU ke **fix seats** de diye jaate hain (`vcpupin`). Koi dusra VM us seat pe nahi baith sakta → speed kabhi kam nahi hoti.
- **Hugepages** = RAM ka **reserved parking**. Server busy ho tab bhi tumhari RAM wahi rehti hai.

**RDP (Windows) ke liye panel kya karega:**
- Windows ki ISO tum upload karoge (license tum/customer ka).
- Panel khud **virtio drivers** andar daal dega (warna Windows disk hi nahi dekhta).
- **Unattended install** = Windows khud install ho jayega, koi "Next Next" nahi.
- RDP khud on, strong password khud banega, alag port milega.
- **Browser-based RDP** = customer ko kuch install nahi karna — panel ke andar hi Windows khul jayega. Saath me `.rdp` file download bhi.
- Panel port check karke batayega "RDP ready ✅".

### 🆕 LXD / Bot Hosting (tumhara naya requirement)

**⚠️ Sabse pehle tumhara correction (maine plan me fix kar diya):**
> Tumne kaha — *"VPS aur VDS jo create hoga wo LXD container NAHI hona chahiye, kyunki LXD container me `lxd init` kaam nahi karta. Mujhe **Proxmox** jaisa chahiye jisme sab kuch supported ho, kuch bhi install kar sakte hain."*
>
> **Ab rule ye hai (master prompt me HARD RULE likh diya):**
> - **VPS aur VDS hamesha asli KVM/QEMU virtual machine honge — kabhi LXC/LXD container nahi.**
> - Customer ko **asli kernel** milega (Proxmox jaisa): kuch bhi install karo, kernel modules load karo, andar Docker/LXD/chhota KVM chalao, VPN/WireGuard lagao, sysctl badlo — **kuch bhi "unsupported" nahi hoga.**
> - **Nested virtualization** expose hoga (`-cpu host` + `kvm=on`) agar host allow kare — aur capability report saaf batayega ki available hai ya nahi.
> - **LXC/LXD containers sirf ek alag saste "Bot Hosting" product me honge**, kabhi "VPS" naam se nahi beche jayenge.

**Ab samjho LXD kya hai:**
> LXC = Linux containers (ek hi OS ke andar chhote-chhote isolated box).
> **LXD/Incus** = un boxon ka **manager**. Ek command me box banao, usme bot chalao:
> `lxc launch ubuntu:22.04 mybot` → `lxc exec mybot bash` → bot start.
> **Nesting** = box ke **andar** box chalana (isliye `security.nesting=true` chahiye).

**Hum 2 tarike se denge:**

**A. "LXD-ready" VPS/VDS** — customer ko VPS milega jisme **LXD pehle se install + setup ho chuka hoga**.
- Storage pool ban chuka hoga, bridge (`lxdbr0`) up hoga, user `lxd` group me hoga → **koi `lxd init` ka wizard nahi, koi sudo nahi**. Customer ki pehli command hi chal jayegi.
- VM card pe badge: **"LXD ready ✅"** + version + kitni jagah khali + **copy-paste quickstart commands**.
- Panel ye bhi dikha sakta hai ki *"is VPS ke andar 3 containers chal rahe hain"*.
- **KVM na ho tab bhi LXD chalega** (containers ko KVM ki zaroorat nahi hoti) — panel block nahi karega, ye baat khud bolega.

**B. "Bot Hosting" product** — panel khud host pe LXD containers banayega (sabse sasta plan, ~2 second me ready).
- **Templates ("eggs")**: Discord.js, Discord.py, Java (JDA), Node.js, Python, n8n, Minecraft — aur **Pterodactyl ke eggs import** bhi ho sakenge.
- Har bot ke liye: file manager, live console, **crash hone pe auto-restart**, env variables ka sundar form, **GitHub repo se 1-click deploy**, backup.
- Bot raat ko crash hua → **Discord/Telegram pe message**: *"your bot went down at 3:12 AM, auto-restarted"*.

**Rule:** UI me kabhi words mix nahi honge — KVM VM / VDS / LXC / LXD / Docker alag-alag clearly likhe jayenge.

# 🌐 IPv4 kaise doge? (tumhara sawaal — Pterodactyl jaisa)

Pehle ek baat samajh lo: **IPv4 free nahi hota.** Ek server ko provider ek (ya do) public IP deta hai. Baaki IPs **kharidne padte hain**. Isliye 4 tarike hain:

| Tarika | Aasaan matlab | Kharcha | Kisko dena |
|---|---|---|---|
| **A. NAT + Port Forwarding** ⭐ (default) | Poori building ka **ek hi main gate** hai. Har flat (VM) ko alag **gate number** milta hai. Customer connect karega `1.2.3.4:22041` pe. | **₹0** | Saste plans, bot hosting — 90% customers |
| **B. Dedicated IPv4 (bridge)** | Har VM ko **apna asli public IP**. Provider se extra IPs kharidne padte hain (Contabo/Hetzner/OVH dete hain). | ₹ per IP | Premium plans, Windows RDP, mail server (rDNS chahiye) |
| **C. Routed subnet / 1:1 NAT** | Provider tumhe ek **poora range** (jaise 8 IPs ka `/29`) tumhare server pe route kar deta hai. Panel us range me se baant deta hai. | Ek saath range ka | Jab tumne subnet kharida ho |
| **D. IPv6** | Naya protocol — provider usually **free me `/64`** deta hai (arab-kharab IPs). Har VM ko asli IPv6 mil sakta hai. | **₹0** | Sabko free me "asli IP" dene ke liye |

**Panel me ye kaise dikhega (admin side):**
`Admin → IP Pool` page — tum IP ya CIDR daaloge + gateway + netmask + bridge. Har IP ka status dikhega: `free` / `assigned` / `reserved`. VM banate waqt panel **khud** ek free IP uthayega, VM delete hone pe **khud wapas** daal dega. Duplicate IP detection (`arping`), CSV import, aur plan rule ("is plan me dedicated IP milega"). Har IP pe **rDNS/PTR** edit kar sakte ho.

**Customer ko kya dikhega:** VM page pe `IPv4: 1.2.3.4` (ya NAT mode me `1.2.3.4:22041`), `IPv6`, `Gateway`, `Netmask`, ready-made `ssh` command, `.rdp` file, copy buttons. NAT mode me ek **port-forward table** bhi hoga — "Add port" button (plan ki limit ke andar).

**Meri salaah (business ke liye):**
1. Shuru me **NAT + port forwarding + free IPv6** se start karo — zero extra kharcha, unlimited customers.
2. Jab paise aane lagein, provider se **5-10 extra IPs** kharido aur "Dedicated IP" ko **₹150-300/month add-on** bana do. Ye sabse aasan upsell hai.
3. Windows RDP plans me dedicated IP default rakho (RDP users ko IP:port pasand nahi aata).
